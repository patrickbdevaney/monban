1. Executive Architectural Synthesis: Resolving the
Post-PHP Paradox
The historical dominance of PHP in the early web was an emergent property of its execution
lifecycle rather than its language design. By initializing and tearing down an isolated memory
arena on every HTTP request, PHP aligned with the economics of multi-tenant shared hosting:
a fatal panic, memory leak, or uncaught exception destroyed only the active request, leaving
the parent daemon and adjacent tenants unharmed. Over the subsequent two decades, the
software industry traded away this disposable, shared-nothing resilience in favor of
long-running, stateful application runtimes—such as Node.js, Python async workers, Java
servlets, and monolithic Go or Rust microservices—to eliminate process-spawning overhead
and achieve high concurrency1.
In an internet increasingly populated and driven by autonomous Large Language Model (LLM)
agents, that architectural trade-off has become a critical liability. Long-running stateful
application servers rely on ambient authority, holding global database connection pools,
environment variable secrets, and persistent heap memory across thousands of concurrent
requests3. When an autonomous agent interacts with such a backend via the Model Context
Protocol (MCP) or REST APIs, a single indirect prompt injection, confused-deputy exploit, or
algorithmic complexity payload can hijack the worker's ambient credentials to exfiltrate
database tables or starve the host of compute resources4.
Simultaneously, the rise of AI software engineering agents inverts the human ergonomics
bottleneck that originally prevented strict, formally verified systems languages from winning
the web in the 1990s. Human developers historically resisted strict borrow checking, explicit
capability schemas, and formal pre-condition and post-condition annotations because manual
proof construction slowed feature velocity7. Conversely, when autonomous coding agents
author backend business logic, compiler strictness and Satisfiability Modulo Theories (SMT)
verification act as deterministic guardrails7. Automated verification workflows such as KVerus
demonstrate that LLM coding assistants paired with formal verifiers can iteratively synthesize,
check, and repair formal proof obligations before a binary is ever allowed to compile7.
The Aegis Architecture defined in this report establishes the "Ironclad Middle Tier"—a
single-binary, drop-in application and gateway server that sits between upstream human
browsers or autonomous MCP agents and downstream battle-tested databases such as
PostgreSQL and SQLite6. Rather than reinventing the relational storage engine or the global
CDN edge, Aegis replaces the vulnerable application server layer (Nginx with PHP-FPM,
Node.js, or FastAPI) with a formally verified Rust host that revives PHP's shared-nothing crash
isolation at sub-millisecond native speed1.

2. Core Subsystem Trade-Offs and Empirical
Resolution
Designing a production-grade server repository requires resolving deep architectural tensions
within the contemporary systems ecosystem. A naive specification that simply combines
disparate crates will fail at compile time due to incompatible asynchronous executors,
C-binding cross-compilation limits, and wire-protocol mismatches1. The following analysis
resolves the six foundational engineering trade-offs required to construct the Aegis stack.
2.1 The Async I/O Boundary: Bridging Thread-Per-Core io_uring and
the Tokio Ecosystem
A central tension in high-performance Rust networking lies between completion-based
io_uring runtimes and readiness-based epoll ecosystems1. Pure thread-per-core runtimes such
as monoio and Datadog's glommio eliminate cross-thread lock contention and voluntary
context switches by pinning each event loop to a physical CPU core and marking tasks as
!Send1. Because io_uring is completion-oriented, buffer ownership must be transferred into
kernel space (DmaBuffer or owned Vec) until the kernel posts a Completion Queue Entry
(CQE), which eliminates syscall transitions when paired with SQPOLL1.
However, an empirical audit of the Rust async ecosystem reveals critical operational constraints
when building a full-stack gateway. Mission-critical protocol libraries—specifically quinn for
QUIC transport and tokio-postgres for pipelined PostgreSQL wire communication—are deeply
architected around Tokio's readiness-based mio wakers and Send + Sync work-stealing tasks1.
Furthermore, while monoio excels in tail-latency proxy microbenchmarks, single-threaded
tokio-uring achieves 370,000 requests per second compared to 270,000 requests per second
for single-threaded monoio in direct comparisons, and scales across cores by spawning
independent per-core executors30. A second constraint arises in embedded storage
contention: the Copy-on-Write (CoW) ACID key-value store redb provides zero-copy MVCC
reads and checksummed B-trees33, making it ideal for the local Session Write-Ahead Log
(WAL). Yet redb performs blocking disk I/O during transactions and permits only a single open
WriteTransaction at a time, meaning that invoking redb writes directly inside an asynchronous
network task stalls the executor thread27.
To resolve both constraints simultaneously, Aegis implements a Split-Plane Sharded Runtime
leveraging the spargio architecture35. The fast-path Ingress and Wasm Sandbox Plane runs on
thread-affine io_uring shards on Linux 6.0+ (with Linux 5.18+ required for core io_uring and
msg_ring paths)35. Each shard owns one pinned worker thread, a dedicated io_uring
Submission and Completion ring, and a thread-local Wasmtime store pool1. When a shard must
interact with the Tokio-bound ecosystem (quinn UDP GSO/GRO streams or tokio-postgres
connection pools) or commit a batch of session WAL entries to redb, it crosses an explicit,
zero-lock spargio::boundary channel30. Cross-shard coordination wakes recipient rings via
kernel IORING_OP_MSG_RING CQE injection rather than userspace mutexes, while a dedicated
Group-Commit WAL thread drains redb write requests sequentially in atomic batches using
io_uring asynchronous fsync operations27.
2.2 Post-Quantum Transport and Zero-Copy Serialization
To defend against Harvest-Now-Decrypt-Later (HNDL) attacks without sacrificing TLS
handshake throughput, Aegis standardizes on rustls configured with the aws-lc-rs
cryptographic provider22. Whereas the legacy ring provider lacks post-quantum key
encapsulation37, aws-lc-rs natively provides FIPS 140-3 validated ML-KEM primitives and
enables the hybrid X25519MLKEM768 and SecP256r1MLKEM768 key exchanges by default24.
For post-quantum authentication and capability signing, Aegis integrates rustls-post-quantum
and the aws-lc-rs unstable::signature module, enabling NIST FIPS 204 ML-DSA-44, ML-DSA-65,
and ML-DSA-87 lattice signatures alongside classical Ed2551923.
A critical build-system constraint is that aws-lc-rs wraps highly optimized C and assembly
routines from AWS-LC and is therefore unavailable on WebAssembly guest targets28.
Consequently, all TLS termination, X25519MLKEM768 decapsulation, and ML-DSA-65 or
Ed25519 signature verifications are strictly executed in the native host binary (aegis-crypto)
prior to sandbox instantiation22. Guest .wasm cartridges receive only pre-verified, strongly
typed capability structures across the Wasm Interface Types (WIT) boundary, eliminating
redundant cryptographic overhead inside the sandbox3.
2.3 Wasmtime Nano-Sandboxing: Pooling Allocators, MPK, and Dual
Fuel-Epoch Preemption
To achieve the density of 10,000+ isolated tenant handlers on commodity hardware with
PHP-style crash immunity, aegis-sandbox embeds wasmtime (v49+ series) and
wasmtime-wasi-http supporting WASI p2 and p3 Component Model interfaces12. Standard
on-demand mmap allocation and Cranelift JIT compilation introduce millisecond latency spikes
that degrade tail latency under bursty agent traffic. Aegis eliminates cold starts by compiling
cartridges ahead-of-time (AOT) into signed native .cwasm artifacts and loading them into a
single process-wide Engine via Module::deserialize with runtime JIT compilation disabled in
production3.
For memory isolation, the Engine is configured with PoolingInstanceAllocator
(PoolingAllocationConfig), which pre-allocates a fixed pool of virtual memory slots, component
tables, and fiber execution stacks12. On x86_64 Linux hosts, Aegis enables the
memory-protection-keys feature (PoolingAllocationConfig::memory_protection_keys), utilizing
hardware Memory Protection Keys for Userspace (PKRU) registers12. Hardware MPK allows the
pooling allocator to compact virtual memory guard regions by striping protection keys across
adjacent slots rather than requiring multi-gigabyte virtual address reservations per instance,
increasing concurrent sandbox density by an order of magnitude at the cost of a minor
register-switch overhead on host-to-guest transitions13.
To prevent compute denial-of-service from runaway agent loops, Aegis combines
deterministic instruction counting with wall-clock rate control5. Relying solely on
Config::consume_fuel traps a guest after a fixed number of instructions (where arithmetic and
memory operations consume 1 unit of fuel while nop, drop, block, and loop consume 0 units)15,
whereas Config::epoch_interruption provides coarse wall-clock deadlines3. Defending against
adversarial agent swarms requires bounding the rate of computation (fuel consumed per
second) alongside total execution fuel5. Aegis therefore enables both consume_fuel(true) and
epoch_interruption(true) alongside Store::fuel_async_yield_interval3. When an epoch tick or
yield interval fires, the Store::epoch_deadline_callback inspects the burned fuel via
consumed_fuel = FUEL - store.get_fuel(), dynamically returning UpdateDeadline::YieldCustom
with a proportional Tokio or io_uring timer delay if an unverified guest exceeds its allocated
compute rate, or immediately trapping and resetting the pooled memory slot via
decommit_queue if the absolute budget is exhausted5.
2.4 Dual-Native Ingress: MCP Streamable HTTP (2026-07-28 Spec)
and Human UI Projection
A foundational requirement for the Aegis server is serving both human browser traffic and
autonomous AI agent tool invocations from a single unified handler definition. In early MCP
deployments (protocol version 2024-11-05), remote servers relied on the HTTP+SSE transport,
which required clients to hold open a persistent GET Server-Sent Events stream while sending
JSON-RPC requests to a separate POST endpoint6. Under sustained multi-agent concurrency,
HTTP+SSE exhibited severe latency degradation—climbing into hundreds of milliseconds—and
throughput collapse, leading to its deprecation in specification version 2025-03-26 and
subsequent stateless refinement in revision 2026-07-286.
Aegis implements the MCP Streamable HTTP specification (2025-03-26 and 2026-07-28
revisions), which sustains approximately 10 ms call latencies at 300+ RPS and supports
completely stateless horizontal scaling6. Every compiled WIT handler registered in Aegis is
automatically projected onto a single unified HTTP endpoint that enforces zero-body header
routing, dynamic stream upgrading, and stateless multi-round-trip continuations6. Per the
2026-07-28 Streamable HTTP specification, MCP clients mirror JSON-RPC metadata directly
into HTTP headers—specifically Mcp-Method, Mcp-Name, and Mcp-Param-{Name} extracted
from primitive integer, string, or boolean tool schema properties annotated with
x-mcp-header6. The aegis-ingress layer strictly validates the Origin header on all incoming
connections (returning HTTP 403 Forbidden on invalid origins to prevent DNS rebinding
attacks) and rejects any x-mcp-header containing carriage return (\r) or line feed (\n) control
characters6. Because method names and target resource parameters are exposed in the HTTP
headers, Aegis evaluates the caller's Datalog capability token at the ingress socket layer before
reading the HTTP body or allocating a Wasmtime Store4.
Each agent POST request operates independently on this single endpoint6. If a Wasm handler
completes synchronously within a single fuel quantum, Aegis returns 200 OK with
application/json6. If the handler emits progress events (notifications/progress), Aegis
dynamically upgrades that specific request's response into a scoped SSE stream6. Closing the
SSE response stream by the client is treated unambiguously by aegis-ingress as request
cancellation, immediately trapping the active Wasmtime Store and discarding its uncommitted
Copy-on-Write memory buffer6. Furthermore, when a server tool requires interactive user
input or client-side LLM sampling (elicitation/create) via Multi-Round-Trip Requests (MRTR),
Aegis does not pin a stateful Wasm instance in RAM waiting for a reply6. Instead, the handler
journals its intermediate state into the redb Session WAL and returns an InputRequiredResult
containing inputRequests6. The Wasm slot returns to the PoolingInstanceAllocator immediately;
when the agent retries the POST with the matching inputResponses and session nonce, Aegis
replays the WAL journal in microseconds and resumes execution seamlessly6.
2.5 Decentralized Capability Security and Economic Metering: AIP
over Biscuit and x402
To eradicate Confused Deputy vulnerabilities and Indirect Prompt Injection privilege escalation,
Aegis replaces bearer JWTs and static API keys with Identity-Bound Capability Tokens (IBCT)
based on the Agent Identity Protocol (AIP) layered atop biscuit-auth (v6.0)4. While raw
biscuit-auth provides an append-only block format signed via Ed25519 and evaluated via a
terminating Datalog engine with scoped rule isolation and unified string interning4, raw Biscuit
defines no identity resolution, no protocol bindings for MCP or HTTP, and no execution
provenance model4.
By implementing the AIP profile over biscuit-auth, Aegis unifies identity, attenuated
authorization, and cryptographic provenance in a single evolvable token chain4. Single-hop
agent calls can utilize Compact Mode (verified in 0.049 ms in Rust compared to 0.189 ms in
Python), whereas multi-hop delegations utilize Chained Mode transmitted via the X-AIP-Token
HTTP header4. In Chained Mode, Block 0 (the authority block) establishes a max_depth
(defaulting to 3), allowed tool scopes such as [tool:search, tool:email], and a compute or
monetary budget17. When an orchestrator agent delegates a subtask to a specialist sub-agent,
it appends an attenuated block offline narrowing the scope to [tool:search] and reducing the
budget (100 <= 500)16. The Biscuit authorizer evaluates all blocks together and rejects any fact
that contradicts an earlier attenuation or exceeds max_depth17.
For high-risk state mutations such as database writes or outbound payments, Aegis enforces
step-up verification via Biscuit third-party blocks (allow if scope("orders:write"),
operation("write"), amr("mfa") trusting authority, ed25519/...)45. An external attestor signs an
amr("mfa") block cryptographically bound to the specific token without ever seeing the token
itself, ensuring that nobody can move the attestation block onto a different token45. Upon
finishing an invocation, the ephemeral worker signs a final Completion Block containing status:
completed and result_hash: sha256:..., producing a single cryptographic audit artifact proving
who authorized the action, through which agents delegation flowed, what constraints applied
at each hop, and the exact output digest4. Additionally, when an unauthenticated external
agent requests a protected MCP tool without an authority token, aegis-ingress responds with
HTTP 402 Payment Required following the x402 protocol standard—maintained by Coinbase
and the x402 Foundation, which has processed over 165 million agent transactions46. Once the
agent signs an atomic USDC payment payload (X-Payment), the host verifies the settlement
and mints an ephemeral Biscuit token parameterized with the exact purchased budget and
fuel_grant facts17.
As the empirical benchmarks confirm, evaluating a three-hop attenuated Biscuit token requires
just 135 µs (0.135 ms), and even a six-hop chain completes in 324 µs—well below the
1-millisecond threshold4. Chained tokens scale linearly at 340 to 380 bytes per delegation
block4. Because aegis-ingress caches parsed public keys in thread-local storage and evaluates
Datalog facts in memory prior to Wasm instantiation, capability verification adds only 0.22 ms
of total overhead to live MCP HTTP calls4.
2.6 The Iron Gate Database Proxy: Compile-Time SQL AST Verification
and Extended PGWire
The ultimate objective of an adversarial agent attack is unauthorized data exfiltration or
corruption in the backend database. Traditional web stacks hand application workers a
connection pool capable of executing arbitrary SQL strings. Aegis severs this attack vector by
introducing aegis-db-gate, an internal database firewall built on pg_query.rs and pgwire
(v0.41.1)11.
The defense operates across both compile time and runtime. During compilation
(aegis-compiler), when an AI coding agent or developer builds a handler cartridge, the Aegis
toolchain scans all database macros using pg_query.rs, which links directly against
PostgreSQL's official C server parser (libpg_query) via its protobuf interface19. Every SQL
statement is parsed into its canonical PostgreSQL Abstract Syntax Tree (Node::SelectStmt,
Node::InsertStmt), guaranteeing 100% compatibility with PostgreSQL syntax19. The compiler
automatically rejects multi-statement queries (split_with_parser), dynamic table or column
interpolation, DDL statements (DROP, ALTER), and bulk COPY operations18. Validated
statements are canonicalized, hashed via BLAKE3 into a 64-bit StmtId, and written into a signed
queries.lock manifest embedded inside the .cwasm cartridge. Furthermore, in the PostgreSQL
wire protocol, the Extended Query sub-protocol requires the database engine to perform
parameter type inference during the Parse phase before parameter values are bound56. While
native PostgreSQL supports this natively, embedded engines like SQLite and DuckDB lack
sufficient APIs to infer variable parameter types without executing the query56. Aegis
overcomes this limitation by extracting the exact parameter types from the Rust macro
call-site and target schema at compile time, storing the parameter OID array directly inside
queries.lock so aegis-db-gate can satisfy Describe and Bind requests without querying SQLite
for type inference11.
At runtime (aegis-db-gate), Wasm guests possess zero network socket access. They interact
with databases either via a typed WIT host import or via a virtualized local pgwire endpoint11.
Within aegis-db-gate, the pgwire SimpleQueryHandler—which accepts raw text strings—is
permanently disabled, and any Simple Query message immediately traps and terminates the
sandbox11. Only the ExtendedQueryHandler (Parse, Bind, Execute, Describe, Sync) is active,
backed by a read-only PortalStore populated exclusively from the cartridge's signed
queries.lock manifest11. Before dispatching the bound portal over the internal tokio-postgres
pool or local SQLite engine, aegis-db-gate extracts the verified principal_id and tenant_id from
the caller's Biscuit token and prepends SET LOCAL app.principal_id = $1; SET LOCAL
app.tenant_id = $2; inside the transaction envelope, guaranteeing mandatory Row-Level
Security (RLS) enforcement on every query11.

3. Repository Architecture and Workspace
Specification
To translate these architectural resolutions into a maintainable software artifact, the repository
(aegis) is structured as a hermetic Rust Cargo workspace divided into a Formally Verified Core
(Verus), a High-Throughput Runtime Data Plane, a Database and Storage Gate, and a
Developer/Agent SDK Toolchain11.

            &&& old(grant).remaining_fuel >= stmt_cost_fuel​
            &&& grant.remaining_fuel == old(grant).remaining_fuel - stmt_cost_fuel​
            &&& remaining == grant.remaining_fuel​
            &&& (grant.is_mutating ==> input_integrity != IntegrityLevel::UntrustedAgentInput)​
        },​
        Err(_) => {​
                         // State remains strictly unmutated on any rejection​
                         *grant == *old(grant)​
                    }​
               }​
     {​
          if grant.allowed_stmt_id != requested_stmt_id {​
               return Err(());​
          }​
          if grant.is_mutating && input_integrity == IntegrityLevel::UntrustedAgentInput {​
               return Err(());​
          }​
          if grant.remaining_fuel < stmt_cost_fuel {​
               return Err(());​
          }​
          grant.remaining_fuel = grant.remaining_fuel - stmt_cost_fuel;​
          Ok(grant.remaining_fuel)​
     }​
     ​
     } // verus!​


4. Formal Verification and Deterministic Simulation
Pipeline
A backend server designed to withstand evolutionary AI cyber warfare cannot rely solely on
manual code review. The Aegis repository enforces a two-stage automated verification
pipeline on every commit and cartridge build.
4.1 Stage 1: Verus SMT Verification and the KVerus Agent Loop
All code in aegis-verified-core and critical state transitions in aegis-db-gate are checked by
cargo-verus25. Verus translates annotated Rust functions into its high-level intermediate
representation (VIR) and emits SMT-LIB queries organized into parallel verification buckets
solved by Z3 (v4.12.5+) and experimentally cvc525. In Verus, calling unwrap() or indexing a slice
carries an implicit precondition; if the SMT solver cannot mathematically prove is_Some(),
is_Ok(), or bounds safety across all possible inputs, compilation halts immediately at the exact
call site and emits a counterexample8.
To make formal verification seamless for developers and AI coding agents building applications
on Aegis, aegis-compiler embeds the KVerus automated proof synthesis workflow7. When an
unverified function is authored, the build tool first extracts dependency-scoped code context
from repository metadata by building a typed directed graph over relevant functions, spec
functions, proof lemmas, structures, and traits7. Next, it retrieves reusable lemmas from both
vstd and project libraries by indexing lemma signatures alongside LLM-generated semantic
summaries7. Finally, the KVerus loop generates candidate proof annotations (requires, ensures,
and loop invariant blocks), checks them with rust_verify, and feeds verifier diagnostics from
sst_to_air.rs back into an error triager and fixer to iteratively repair failed proof attempts7.
Crucially, the LLM output is never treated as a trusted artifact: the Verus SMT checker remains
the uncompromising mathematical authority for proof validity before ghost code is erased and
the executable binary is emitted7.
4.2 Stage 2: Deterministic Simulation Testing (DST) via madsim
While Verus proves functional correctness, panic-freedom, and memory safety within
individual modules, SMT solvers do not verify distributed liveness or absence of deadlocks
across asynchronous I/O boundaries by default8. To verify the interaction between io_uring
socket drops, Wasmtime async yields, redb WAL crash recovery, and PostgreSQL connection
pooling, aegis-sim implements FoundationDB-style Deterministic Simulation Testing using
madsim26.
To preserve total determinism under simulation, all core Aegis state machines are architected
without direct access to system clocks or untracked OS-thread primitives, which would
otherwise break deterministic replay26. State machines perceive time exclusively through
explicit timestamps passed into tick calls by the simulation message bus, allowing the simulator
to compress hours of timeouts and backoff intervals into microseconds26. Every random
decision in the system—including event reordering, packet drops, simulated client SSE
disconnects, x402 facilitator delays, and torn WAL writes—draws from a single pseudo-random
number generator initialized with a 64-bit seed printed at the start of each CI run26. In
continuous integration, aegis-sim executes thousands of simulated hours of chaotic
multi-agent traffic overnight; if a concurrency bug, livelock, or calculation error surfaces,
re-running the test with the same 64-bit seed reproduces the exact instruction interleaving
deterministically26.

5.1 Detailed Execution Directives for Critical Path Engineering
Step 1: Bootstrapping the Verus Toolchain and Core Invariants (Weeks 1–3)
Execution begins by pinning the Rust toolchain and Z3 v4.12.5 in a reproducible build
environment58. Engineers construct crates/aegis-verified-core with #![no_std] compatibility so
it remains strictly isolated from OS syscalls. Using Verus linear ghost types, the team formalizes
the CapabilityGrant and CoWTransactionArena structures62. Every state transition function
carries an explicit ensures clause proving that on any error branch, *state ==
*old(state)—mathematically guaranteeing the PHP shared-nothing invariant that failed or
aborted requests never mutate host state8.
Step 2: Engineering the Wasmtime Pooling Sandbox and Fuel/Epoch Loop (Weeks
4–6)
In crates/aegis-sandbox, engineers initialize a single process-wide wasmtime::Engine
configured with PoolingInstanceAllocator3. On x86_64 Linux targets,
PoolingAllocationConfig::memory_protection_keys is enabled so hardware PKRU registers
isolate adjacent linear memories without exhausting virtual address space12. Both
config.consume_fuel(true) and config.epoch_interruption(true) are activated on the engine3. A
background hardware timer increments the engine epoch every millisecond, while each
request Store is configured with store.fuel_async_yield_interval(Some(50_000)) and an
epoch_deadline_callback that compares burned fuel (FUEL - store.get_fuel()) against the
caller's Biscuit fuel_grant rate, yielding via UpdateDeadline::YieldCustom or trapping cleanly
upon budget exhaustion5.
Step 3: Implementing the Compile-Time AST Extractor and PGWire Extended
Proxy (Weeks 7–10)
In crates/aegis-compiler, the build CLI integrates pg_query.rs (libpg_query) to parse all
procedural SQL macros via pg_query::parse at compile time19. The AST traversal verifies that
each query consists of a single SelectStmt, InsertStmt, UpdateStmt, or DeleteStmt, rejecting
multi-statement strings and DDL mutations53. The compiler hashes the canonical AST with
BLAKE3 to generate the 64-bit StmtId and records the explicit PostgreSQL parameter Type
OIDs into queries.lock, overcoming SQLite's inability to perform parameter type inference
during Extended Query Parse messages56. In crates/aegis-db-gate, engineers implement
pgwire's ExtendedQueryHandler backed by an immutable PortalStore populated from
queries.lock, while wiring SimpleQueryHandler::do_query to return an immediate fatal protocol
rejection11.
Step 4: Wiring the Spargio io_uring Ingress and MCP Streamable HTTP Normalizer
(Weeks 11–14)
In crates/aegis-ingress, the server initializes one spargio io_uring shard per physical CPU core,
utilizing msg_ring CQE injection for cross-shard wakeups1. The TLS acceptor is constructed
using rustls with the default aws-lc-rs provider and X25519MLKEM768 prioritized in the key
exchange group list22. When handling traffic on the unified MCP Streamable HTTP (2026-07-28)
endpoint, the ingress pipeline first validates the Origin header to block DNS rebinding, then
extracts Mcp-Method, Mcp-Name, and Mcp-Param-* headers while rejecting any header
containing \r or \n characters6. Next, the gate extracts the X-AIP-Token header—or returns an
HTTP 402 Payment Required challenge carrying an x402 USDC invoice if unauthenticated—and
evaluates the Biscuit Datalog policy against the Mcp-* header facts before allocating a
Wasmtime Store or reading the HTTP body4. Validated requests are dispatched into the
shard-local Wasmtime pool, dynamically upgrading to a request-scoped SSE stream if progress
notifications are emitted and wiring the transport disconnect signal directly to cancel the active
Wasmtime store6.

6. Conclusions and Architectural Synthesis
The Aegis server architecture demonstrates that the historical compromise between developer
velocity, runtime performance, and formal security is obsolete in the agentic era. By scoping
the software product strictly to the Application and Gateway Server Layer—sitting between
upstream human or agent protocols and downstream PostgreSQL or SQLite databases—the
architecture avoids the intractability of reinventing relational storage or global network transit
while sealing the exact middle-tier attack surface where modern web applications fail6.
Three structural conclusions govern the implementation and long-term durability of this
repository. First, disposable execution is mandatory for agentic infrastructure. Just as
mod_php survived buggy human code on shared hosts by discarding request memory after
every HTTP call, an agent-facing backend must treat every tool call and HTTP request as
potentially adversarial. Combining wasmtime's PoolingInstanceAllocator and hardware Memory
Protection Keys (PKRU) with a redb Copy-on-Write Session WAL achieves PHP's crash immunity
and hot-swap deployment fluidity (< 15 µs instantiation) at native Rust throughput12.
Second, zero-body header routing and compile-time AST gates eradicate confused-deputy
exploits. By pairing the MCP Streamable HTTP (2026-07-28) header-mirroring specification
(Mcp-Method, Mcp-Name, Mcp-Param-*) with biscuit-auth and AIP Datalog capability tokens
(< 325 µs verification across 6 delegation hops) alongside pg_query.rs compile-time SQL AST
registration, Aegis makes unauthorized tool execution and SQL injection structurally
impossible—even if an autonomous agent's context window is completely hijacked by indirect
prompt injection4.
Finally, formal verification is force-multiplied by AI coding agents. Applying Verus (Z3 SMT
verification) to the core authorization and state-transition kernel (aegis-verified-core) and
madsim deterministic simulation testing to the asynchronous runtime boundary eliminates
entire classes of memory, concurrency, and state-machine bugs at compile time9. Integrating
the KVerus automated proof-refinement loop into the SDK toolchain ensures that AI coding
agents building applications on Aegis are mathematically constrained to produce provably
sound, panic-free backend cartridges7.
