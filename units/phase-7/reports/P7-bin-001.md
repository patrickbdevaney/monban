| PROXY v2 | `front.rs`, feature `proxy-protocol` | Before TLS. Trust on the TCP peer only (`ProxyProtocol::admits`). Trusted: the header is required (read until `parse_v2` is not `Incomplete`, bounded by `MAX_HEADER_LEN`); any error, `!stream_accept()` (DGRAM), EOF or the deadline closes with nothing sent; `source()` (TCP4/TCP6 PROXY only, else the TCP peer) becomes the peer handed to the transport, so admission S0..S6 and the app see it (PROXY-2). Audit `proxy.accept` (object = listener, `peer`, `via`, outcome allow) is appended durably (off the async workers) before anything else; a failed append refuses the connection. ## The scaling bench needs a config change (bench/ is outside this scope)

With admission wired, `bench/scaling/run --cores 1,2,4,8,16,18` PASSes when the harness's `config_doc` adds two
members. Exactly this, in `bench/scaling/scaling.py` `config_doc`, next to `"admin"`:

```python
"admission": {"per_ip": {"rate_per_s": 1000000, "burst": 10000000}},
"limits": {"max_streams_per_conn": 100000},
```

- `admission.per_ip` lifts the S1 per-IP limit (one source address, h2load). With it alone, admission rejects went
  to 0, but every point above 1 core still had 326..450 errors: 32 connections × the golden `max_streams_per_conn`
  10 000 = exactly the 320 000 responses per 10 s the P7-scaling-001 report saw as a "client-side ceiling". The
  transport ends each connection at 10 000 streams and h2load does not reconnect, so the streams in flight error.
- `limits.max_streams_per_conn` (F8 max 100 000) lifts that.

## Not servable within scope: MariaDB requests

The native data plane runs every op through the F4 denylist scan (`aegis_data_ir::denied_in_sql(EngineFamily, sql)`)
and the app's allowlist lock (`Allowlist::parse` + family check). aegis-data-ir has no `EngineFamily` for MariaDB
(Sqlite, Postgres, Redis, Valkey only), and apps/notes ships `allowlist.notes-sqlite.lock` and `-pg.lock` only. Serving
MariaDB requests would mean running SQL with neither check, which is a weakening, so aegis-bin boots a mariadb backend
as far as the adapter allows (connect, version gate, session pin, live schema gate) and then refuses with exit 78. To
make it servable: an `EngineFamily::Mariadb` with a MySQL denylist (aegis-data-ir, L2, spec author) and a verified
`allowlist.notes-mariadb.lock` (apps/notes). The executor would then be a per-scope connection (the adapter has no pool
and no cancel), reused only when `is_reusable()`.

CockroachDB reuses the PostgreSQL denylist and lock: it speaks the PostgreSQL dialect, the lock lines are IR op shapes,
and the crdb renderer differs from the PG one only in the upsert guard. The integrator should confirm that reading.

## Residuals and follow-ups

- **bench/scaling `config_doc`**: the two members above (integrator / P7-scaling-001 owner).
- **MariaDB serving**: the EngineFamily + allowlist lock above.
- **crdb SERIALIZABLE retry**: `crdb::run_serializable` retries a whole transaction, but the scope's transaction is
  driven op by op by the SDK host, so a retry would have to re-run the app handler. 40001 surfaces as a conflict
  (fail closed). A handler-level retry belongs to aegis-adapter-host.
- **MTC selection through aegis-bin** is exercised by a smoke run (an x509 credential served through the selector, a
  mismatched key refused with 78) but no gate drives `trust_anchors` through aegis-bin: `cred-select` drives the
  selector through tls-subject. A cred-select mode against aegis-bin would close that.
- **L4 splice idle timeout** after routing is implemented but not exercised by any oracle (proxy-l4 README limit).
- **Rungs**: PROXY-1..3 and L4-1..2 at R2 on the proxy-l4 corpus, FRONT-1 at R2 on the front-equiv corpus, both on
  one host; the wire parsers' bounds are P7-wire-001's Kani claims. The crdb wiring is R1 (one live test); MariaDB is
  boot checks only. rustls, tokio, the kernel io_uring surface and io-uring 0.7.15 are trusted, not verified.
